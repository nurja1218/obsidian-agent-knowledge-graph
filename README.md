# obsidian-agent-knowledge-graph

**brain-vault** — Obsidian vault 하나를 AI 코딩 에이전트(Claude Code)의 **장기 기억이자 작업 기록**으로 쓰고,
노트를 **노드 · 속성 · 시간 엣지가 있는 지식그래프**로 쌓아 에이전트가 세션마다 읽고 쓰게 만든 구조입니다.
2026-05-15 부터 매일 쓰고 있고(vault 커밋 1,837개), 이 레포는 그 구조 · 규칙 · 도구를 회사 내용 없이 정리한 것입니다.

> 숫자는 모두 2026-11-03 내 vault 를 `tools/graph.py` 와 스크립트로 잰 값입니다. 노트 본문은 공개하지 않습니다.

![전체 구조](docs/bv-overview.svg)

## 왜 이렇게 만들었나

- 에이전트는 세션이 끝나면 아무것도 기억하지 못합니다. 남는 건 파일뿐입니다.
- 처음엔 노트를 폴더에만 쌓았고, 도입 전 실측(2026-07-01) 노트 282개 중 **74% 가 어떤 노트와도 이어지지 않은 고아**였습니다.
- 에이전트는 그래프 그림을 보지 못하고 **frontmatter 를 읽습니다.** 그래서 목표를 "보기 좋은 그래프"가 아니라 **에이전트가 따라갈 수 있는 타입 있는 엣지와 시간 축**으로 잡았습니다. 사람은 같은 파일을 Obsidian 그래프 · 백링크 · 속성 패널로 봅니다.

## 세 층

| 층 | 위치 | 노드 | 속성 | 엣지 |
|---|---|---|---|---|
| 기억 | `memory/` | 사실 노트 299 (한 사실 = 한 파일) · 허브 `MEMORY.md` 1 · 색인 6 | `type`(프로젝트 142 · 피드백 106 · 참조 44) · `modified` · `originSessionId` · `description` | 본문 `[[링크]]` 507 (연결 485) |
| 작업 | `projects/<레포>/<도메인>/` | 노트 913 (도메인 허브 66 포함) | `domain`(913) · `status` · `created`(742) · `tags` · `type` | `moc` 828 · `depends-on` 925 · `superseded-by` 59 · `implements` 456 노트 |
| 설정 | `claude-config/` | 규칙 · 훅 · 스킬 | | `~/.claude/` 가 심볼릭 링크로 가리킴 — 기기 · 계정이 달라도 같은 규칙 |

커리어 노트(`personal/career/`)는 근거가 된 작업 노트를 `depends-on` 으로 가리킵니다.

## 기억 층 — 허브 → 색인 → 사실

![기억 층](docs/bv-memory.svg)

- **허브 `MEMORY.md`** 는 설정(`autoMemoryDirectory`)으로 모든 세션에 자동으로 들어갑니다. 허브에는 내용이 아니라 **한 줄 요약 + 링크**만 둡니다(길면 잘려서 로드되기 때문).
- 세션은 작업과 관련된 **색인만** 열고, 색인에서 사실 노트로 내려갑니다.
- 사실 노트끼리는 본문 `[[링크]]` 로 잇습니다. 가장 많이 참조된 노트는 규칙 "단정 전에 경로 전체를 본다"(19회).
- 링크만 있고 파일이 없는 22개는 오류가 아니라 **아직 쓰지 않은 기억** 표시입니다.
- 쓰는 규칙: 새 사실은 파일 1개 + 허브 한 줄 / 같은 내용이 있으면 새로 만들지 않고 고친다 / 틀린 기억은 지운다 / 결정 · 교정은 **이유와 적용 방법**을 같이 적는다.

## 작업 층과 시간 축

![작업 층과 시간 축](docs/bv-time.svg)

| 시간 정보 | 어떻게 | 실측 |
|---|---|---|
| **대체 엣지** `superseded-by` | 옛 노트 → 새 노트. 에이전트는 체인 끝을 "지금 기준"으로 읽는다 | 59개 · 체인 37개 · 가장 긴 체인 = **세션 인계 노트 15개 (9/30 → 10/17)** |
| 수명 `status` | draft → active · in-progress → done · implemented → archived | draft 64 · archived 64 · active 55 · done 39 … |
| 생성 · 갱신 시각 | 작업 노트 `created` / `updated`, 기억 `modified` | 742 / 77 / 159 |
| 출처 세션 | 기억 `originSessionId` — 언제 어느 대화에서 알게 된 사실인가 | 185 |
| 날짜 파일 이름 | 결정 · 인계 · 장애 노트는 `YYYY-MM-DD-` 로 시작 | 232 |

세션이 끝날 때 인계 노트를 쓰고 이전 인계 노트에 `superseded-by` 를 겁니다. 다음 세션은 체인 끝 하나만 읽으면 현재 상태를 알고, 필요하면 거슬러 올라가 "왜 그렇게 됐는지"를 봅니다.

**엣지 규칙**
- 엣지는 `moc` · `depends-on` · `superseded-by` · `implements` 4종만. 이유를 한 줄로 못 적는 `related` 는 쓰지 않는다.
- **없는 관계를 지어내지 않는다.** 엣지는 기계가 추론하지 않고, 에이전트가 노트를 읽고 직접 적는다.
- 새 노트가 자동으로 편입되도록 전역 규칙과 노트 작성 스킬에 이 frontmatter 를 박아 두었다.

스키마: [schema/SCHEMA.md](schema/SCHEMA.md)

## 에이전트가 읽는 경로 (실제 배선)

1. 세션 시작 — `MEMORY.md` 자동 로드 (`autoMemoryDirectory`)
2. 세션 시작 훅 `vault-routing-reminder.sh` — 작업 중인 레포에 맞는 vault 폴더를 찾아 "노트 목록 → `_index.md` → 최근 결정 3개를 먼저 읽어라"를 넣는다
3. 작업 중 — 색인 → 사실 노트, `domain` · MOC → `depends-on` 을 따라 필요한 노트만 연다. 대체된 노트면 체인 끝으로 간다
4. 세션 끝 — 새 사실 · 결정 · 인계를 위 규칙대로 쓴다. vault 는 obsidian-git 이 자동으로 커밋 · 푸시한다

## 작업 방식 — 명세 체인과 세션 인계

![작업 방식](docs/bv-workflow.svg)

**명세 체인** — 큰 작업은 코드를 쓰기 전에 명세서부터. 명세서도 vault 노드(`domain` · `moc` · `implements`)로 저장된다.

1. `/spec-docs` — 요청 → 코드 분석 → 명세서(Phase · 완료 기준 · 용어 사전). 구현하지 않는다.
2. `/spec-review` — 다른 모델들에게 같은 명세를 비판시키고(1라운드), 서로의 답을 비판시킨다(2라운드). 보안 관점은 따로. 합성할 때는 외부 의견을 먼저 읽고 내 판단과 **다른 점만** 남긴다.
3. `/spec-run` — Phase 별 실행. 3파일 이상은 격리된 작업 공간(worktree)의 워커에게. Phase 가 끝날 때마다 변경 이유 · 영향 범위 · 검증 결과 · 남은 위험 4항목.
4. `/spec-verify` — 같은 교차 비판 + 프로젝트 기준 검토. 검증 명령 통과 · 지적 0건이 될 때까지 최대 3라운드, 지적별 판정은 명세서 끝에 기록.

**세션 인계** — 세션 사이에 기억은 없고 재구성만 있다. 그래서 기억을 흉내내지 않고 **싸게 다시 확인하게** 넘긴다.

1. `/handoff-out` (세션 끝) — 이번 세션 산출물이 vault 에 실제로 기록됐는지 검색으로 감사하고, 빠진 것을 기록한 뒤 인계서를 쓴다.
   - 다시 볼 수 있는 것(PR · 브랜치 · 파일 · 배포 상태)은 결론 대신 **명령 + 기대값**, 낡는 속도 태그 `[시간]` · `[일]` · `[상시]`
   - 다시 볼 수 없는 것은 본문에 — **결정 · 기각된 제안 · 실패한 시도 · 사용자가 말로 준 제약**
   - 코드블럭으로 출력 + `handoff/` 노드로 저장. 이어 쓰면 이전 인계에 `superseded-by`
2. `/handoff-in` (새 세션) — 인계서의 명령을 실제로 실행해 대조한다(`[시간]` 부터). 현재 상태는 실측이 인계서보다 우선. 불일치를 근거와 함께 보고하고 **착수하지 않고 대기**.

실측(2026-11-03): 인계 노트 136개(2026-08 ~ 11), 그중 이어 쓴 39개에 `superseded-by`. 명세 노트 202개. 다른 모델 교차 리뷰 기록이 남은 명세는 2건.

## 질의 · 점검 도구 `tools/graph.py`

그래프를 따라가는 일을 지금까지는 에이전트가 frontmatter 를 직접 읽어서 했습니다. 이 레포를 만들며 그 일을 하는 도구를 따로 만들었습니다 (Python 표준 라이브러리만, `--json` 지원).

```bash
python3 tools/graph.py stats   <vault>                  # 노드 · 엣지 · 허브 수, 고아 비율
python3 tools/graph.py query   <vault> --domain <slug>  # 도메인 노트 + depends-on 으로 끌려오는 노트, 대체된 노트 표시
python3 tools/graph.py current <vault> <note>           # superseded-by 를 따라 현재 기준 노트
python3 tools/graph.py lint    <vault>                  # 끊긴 엣지 · 판정 불가(본문 링크 포함) · 새로 깨진 본문 링크 · related 사용 · 대체 순환
```

`stats` · `lint` 는 위키 링크 `[[x]]` 와 마크다운 링크 `[제목](x.md)` 을 모두 읽는다. 링크는 **Obsidian 앱과 똑같이** 푼다(앱의 `getLinkpathDest`) — 대소문자 무시, 정확한 경로가 맞으면 그 파일, 아니면 링크를 건 노트의 폴더 안 → 밖 순서로 각각 경로가 짧은 파일. 같은 이름이 여럿인데 고른 파일이 링크 건 노트와 같은 폴더가 아니면 `ambiguous` 로 알린다(다른 곳에 같은 이름 파일이 생기면 조용히 다른 노트로 바뀌는 링크). 깨진 본문 링크는 처음 한 번 `--update-baseline` 으로 기준 목록(`<vault>/.graph-lint-baseline.json`)을 만들고 그 뒤 **새로 깨진 것만** 알린다. 설정 폴더(`claude-config`, `.work`)는 노트로 세지 않지만 링크 대상 후보로는 본다(Obsidian 이 보므로).

## 이 레포를 만들며 vault 를 고친 기록 (2026-11-03)

도구를 실제 vault 에 돌리자 "반쪽"인 곳이 드러났고, 고친 뒤 다시 쟀습니다.

| 지표 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `domain` 있는 작업 노트 | 805 / 895 | **913 / 913** |
| 도메인 허브 | 49 | **66** |
| `moc` · `depends-on` 엣지 (`projects/`) | 663 · 885 | 828 · 925 |
| 폐기한 `related` 필드 | 24 | **0** |
| 끊긴 · 판정 불가 엣지 (vault 전체) | 17 | **0** |
| 고아 노트 비율 | `projects/` 9.5% · 전체 18.8% | `projects/` **1.1%** · 전체 **2.5%** |

> 전체 비율의 하락은 둘이 섞여 있다 — 노트를 고친 효과 18.8% → 14.1%, 도구를 고친 효과(마크다운 링크 인식 · 설정 폴더 제외) 14.1% → 4.0%, 남은 노트에 허브 연결 4.0% → 2.5%. `projects/` 는 노트 수정으로 9.5% → 2.2%, 도구 수정과 허브 연결로 2.2% → 1.1%.

**무엇이 문제였나**
- 노트 — Obsidian 이 해석하지 못하는 상대경로 링크 4 · 없는 허브를 가리키는 `moc` 9 · 같은 이름 `_index` 4 · 허브 없는 도메인 17 · `domain` 없는 부속 자료(리뷰에 보낸 프롬프트 · 벤치 데이터 · 자동 생성 코드맵) 90 · `related` 24
- 도구 — `[제목](x.md)` 링크를 읽지 않아 기억 층의 허브 → 색인 → 사실 연결이 통째로 빠져 있었고, 같은 폴더 우선 규칙이 없었고, 스킬 · 규칙 문서를 노트로 셌다

**어떻게 고쳤나 (지어내지 않는 선에서)**
- 부속 자료는 같은 폴더 노트의 `domain` 을 따라 허브에만 연결했다 — 새 `depends-on` 은 만들지 않았다
- `related` 는 대상이 본문에서 근거로 인용되거나 같은 명세 폴더의 상위 명세일 때만 `depends-on` 으로, 나머지는 본문 "관련 노트" 줄로 옮겼다(관계 종류를 주장하지 않음)
- 남은 고아는 외부 원문 사본과 개인 노트 — 연결하지 않았다
- 재발 방지 — 전역 규칙에 `query` · `current` · `lint` 사용을 넣고, 인계 스킬 마지막 단계에 "`lint` 새 문제 0건"을 넣었다

### 두 번째 수리 — 이름 겹침 (2026-11-03 저녁)

새 기능 명세가 기존 기능과 같은 파일 이름(`00-spec.md`)으로 만들어지면서, 다른 폴더에서 이름만으로 건 옛 링크가 어느 파일인지 애매해졌다. 파일 내용은 섞이지 않았다.

**왜 못 잡았나**
- 명세 작성 스킬이 기능마다 같은 파일 이름을 쓰게 했다
- `lint` 가 frontmatter 링크만 보고 본문 링크는 보지 않았다
- 도구의 이름 해석 규칙(같은 폴더 → 가장 긴 공통 경로, 대소문자 구분)이 Obsidian 과 달라서, `lint` 가 통과여도 Obsidian 에서는 다른 노트가 열릴 수 있었다

**도구를 Obsidian 규칙으로 바꾸자 드러난 것**
- 애매한 링크 62개
  - 20개는 같은 이름 허브 3쌍 때문이었다. 위 첫 수리에서 만든 허브 3개가 다른 폴더의 기존 허브와 이름이 같았다 → 기존 허브 내용으로 합쳐 하나로
  - 나머지 42개는 원래 가리키려던 파일의 전체 경로 `[[경로|이름]]` 로 고정
- 그 42개 중 **34개는 Obsidian 에서 실제로 의도와 다른 노트를 열고 있었다**
  - 30개는 기억 층 노트가 대소문자만 다른 같은 이름(예: `abc-123-x` vs `ABC-123-x`)이라 명세 링크를 가로챈 것
- `/`로 시작하는 절대경로 마크다운 링크 19개(Obsidian 에서 안 열림) → 상대경로로

**재발 방지**
- 명세 스킬: 파일 이름 앞에 기능 이름(`<기능>-spec.md`)
- vault 규칙: 파일 이름은 vault 전체에서 하나뿐(대소문자 무시)
- `lint`: 본문 링크 `ambiguous` + 새로 깨진 본문 링크(기준 목록 130건)
- 회귀 시험: `mv` 로 이름 바꾸기 → 깨진 링크 19개를 잡음 · 다른 폴더에 같은 이름 파일 만들기 → 애매한 링크 2개를 잡음

- 사람(인물) 노드는 없다. 지금 그래프는 사실 · 작업 · 결정 · 코드 사이의 관계만 다룬다.
- 엣지 품질은 노트를 쓰는 쪽(에이전트)의 규칙 준수에 달려 있다 — 자동 추론은 일부러 하지 않는다.
- `graph.py` 의 frontmatter 파서는 YAML 일부(`key: value`, 인라인 · 블록 목록)만 읽는다.
- 도메인 허브의 Bases 표는 Obsidian 화면용이다.

회사 코드 · 노트 본문 · 서비스 이름은 들어 있지 않습니다. 그림 속 이름은 일반화했고 숫자와 모양은 실제 그대로입니다.
