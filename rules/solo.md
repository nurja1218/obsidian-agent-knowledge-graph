# Solo 작업 4원칙 (Layer 1 보강)

Main Claude가 *직접 코드를 작성·수정*할 때 적용하는 행동 원칙. 카파시(Andrej Karpathy)의 CLAUDE.md guidelines를 기반으로 우리 3-Layer 시스템에 맞게 변형.

> **트레이드오프 인지:** 이 원칙들은 "속도보다 신중함"을 우선한다. trivial 작업(타입 오타, 1줄 import 수정 등)에는 판단력으로 일부 생략 가능. 그러나 *50줄+ 변경·새 모듈·추상화 도입* 같은 작업에는 반드시 적용.

---

## §1. Think Before Coding — 코드 작성 전 사고

**가정을 명시하라. 혼란을 숨기지 마라. 트레이드오프를 표면화하라.**

구현 시작 전:
- 어떤 가정을 하고 있는지 *명시*. 불확실하면 *질문*하라.
- 해석이 여럿이라면 모두 제시 — 묵묵히 하나를 고르지 마라.
- 더 단순한 접근이 있으면 *말하라*. 정당화될 때 *push back*하라.
- 명확하지 않은 게 있으면 *멈춰라*. 무엇이 혼란스러운지 짚고 물어라.

**적용 가이드:**
- 사용자 요청에 *모호한 단어*(예: "최적화", "정리", "개선")가 있으면 *구체적으로 무엇을 의미하는지* 먼저 확인
- 작업 시작 전 한 줄 가정 명시: *"이 작업이 [X]를 의미한다고 가정. 다른 해석 있으면 알려주세요."*
- 더 작은 변경으로 같은 목적 달성 가능하면 *그 옵션도* 제시

---

## §2. Simplicity First — 단순성 우선

**문제를 푸는 최소 코드. 추측성 기능 금지.**

- 요청한 것 외 *기능 추가 금지*.
- 단일 사용 코드에 *추상화 금지*.
- 요청 안 한 "유연성"·"설정 가능성" 추가 금지.
- *불가능한 시나리오*에 대한 에러 처리 금지.
- 200줄 작성했는데 50줄로 가능하면 *재작성*.

**Self-check 휴리스틱:**
- **"선배 엔지니어가 이걸 over-complicated이라 할까?"** → Yes면 단순화.
- **"세 줄이면 충분한 것을 클래스로 만들지 않았나?"**
- **"이 추상화가 *지금* 두 번 이상 쓰이나? 아니면 *언젠가* 쓰일 것에 대비?"** → 후자면 제거.

**경계 인지:**
- *명세서 Acceptance Criteria*에 명시된 것까지만. 명시 안 된 "있으면 좋겠지" 기능 — 사용자에게 묻지 않고 추가 금지.

## §3. Surgical Changes — 외과 수술적 변경

**필요한 것만 건드려라. 자기가 만든 mess만 정리하라.**

기존 코드 편집 시:
- 인접한 코드·주석·포맷팅 "개선" *금지*.
- 망가지지 않은 것 *refactor 금지*.
- 자기 스타일이 더 낫다고 생각해도 *기존 스타일 유지*.
- 무관한 dead code가 보이면 *언급만* — 삭제하지 마라.

자기 변경이 만든 orphan은:
- *자기 변경이 미사용으로 만든* import/변수/함수만 제거.
- 사전부터 있던 dead code는 사용자가 요청 안 했으면 *건드리지 마라*.

**가장 강력한 self-test:**
> **"모든 변경 line이 사용자 요청에 *직접* 추적 가능해야 한다."**
>
> diff를 보고 line마다 *"이건 요청 X를 위한 거다"*라고 매핑할 수 없으면, 그 line은 군더더기 — 삭제하라.

**적용 가이드:**
- *작업 완료 후 diff 자체 검토*: 모든 hunk가 요청에 매핑되나?
- 매핑 안 되는 hunk는 *분리해서 사용자에게 별도 제안* — 같은 PR/commit에 묻지 마라.

## §4. Goal-Driven Execution — 목표 주도 실행

**성공 기준을 정의하라. 검증될 때까지 루프 돌려라.**

작업을 *검증 가능한 목표*로 변환:
- "validation 추가" → "잘못된 입력에 대한 테스트 작성 → 통과시키기"
- "버그 고쳐" → "버그 재현 테스트 작성 → 통과시키기"
- "X refactor" → "변경 전후 테스트 통과 보장"

다중 단계 작업은 *plan + verify* 명시:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

**강한 success criteria**: 독립적으로 loop 가능 (사용자 개입 최소).
**약한 criteria** ("일단 작동하게"): 매번 사용자 확인 필요 → 작업 지연.

**우리 환경에서의 적용:**
- 코드 변경 → `npx tsc --noEmit` + `pnpm lint` 0 errors 확인 (verification-before-completion)
- 기능 변경 → 가능한 한 spec 명세에 Acceptance Criteria 명시
- spec 워크플로우는 이미 이 패턴을 내장 — Solo 작업에서도 같은 원칙 적용
