# ⛔ 근거 없는 진술 금지 (BLOCKER, 모든 프로젝트 공통)

사용자 지시(2026-08-14): **"추정으로 답하지 마라. 추정할 거면 최소한 뭐 하나라도 근거를 갖고 말해라.
근거를 코드에서 찾든 vault 문서에서 찾든 외부 레퍼런스에서 찾든 근거 갖고 말해라."**

이 규칙은 답변 스타일 권고가 아니라 **강제 조건**이다. 반복된 오판으로 사용자가 명시적으로 요구했다.

## 규칙

1. **모든 사실 주장에 근거 출처를 붙인다.** 셋 중 하나여야 한다.
   - **코드**: `file:line` 과 그 줄이 말하는 바
   - **실측**: 실행한 명령/쿼리 + 그 출력 (n 회, 어떤 조건)
   - **문서·외부 레퍼런스**: vault 노트 경로, 공식 문서 URL, 라이브러리 소스 경로

2. **근거가 없으면 "추정" 이라고 명시하고, 그 자리에서 확인 방법을 함께 제시한다.**
   - ❌ "global 이면 다 될 겁니다"
   - ✅ "`@langchain/google-common/dist/connection.js:107` 이 `location==='global'` 일 때
     `aiplatform.googleapis.com` 으로 라우팅한다 — 코드 확인함"
   - ✅ "이건 확인 안 했습니다. `<명령>` 으로 확인 가능합니다"

3. **확인 범위를 문장에 붙인다.** "확인했습니다" 는 도구로 값을 본 것에만 쓴다.
   - "configmap 기준", "n=5", "dev 실물 페이로드 기준", "production 태그만 조회"

4. **한 곳만 보고 단정하지 않는다.** 결론을 말하기 전에
   *"이 결론이 틀리려면 무엇이 사실이어야 하나"* 를 2~3개 적고 그것부터 확인한다.

5. **도구가 '없다'고 하면 도구를 먼저 의심한다.** 부정 결과(0건·키 없음·미발견)는
   **다른 방법으로 한 번 더** 확인하기 전까지 결론이 아니다.

6. **번복은 즉시, 근거와 함께.** 틀린 게 드러나면 변명 없이 철회하고 무엇을 잘못 봤는지 한 줄로 남긴다.

## 실제로 밟은 실패 (근거 없는 단정 → 번복)

| 무엇을 말했나 | 무엇을 안 봤나 | 결과 |
|---|---|---|
| "서비스 A 는 설정 키가 없다" | 공용(통합) 시크릿 | 오판 |
| "dev DDL 적용 완료" | dev RDS 가 2개 | 다른 dev 환경 로그인 500 |
| "①로 KB 미준수 해결됨 (5/5)" | 실제 운영 페이로드(교정블록 20행·FM 5202자·도메인 불일치) | 실전 0/5, 번복 |
| "①은 효과 없음 (0/5)" | 원본 실험의 배치·문구를 그대로 쓰지 않음 | 다시 번복 |
| "configmap 에 태그 키 없음" ×3 | zsh `$b:a` 수식자로 명령이 깨진 것 | 오판 |
| "검색 0건이므로 없음" | 셸 grep 의 binary 오분류 | 오판 |
| "다른 터미널 앱에서도 Ctrl+V 로 이미지 붙여넣기 된다" (2026-10-20) | 그 앱에서 실제로 해 보지 않음 · 문서에도 없음 | 사용자가 해 보니 안 됨, 번복 |
| "떠 있는 세션 끄고 → 다른 계정으로 resume" 안내 (2026-10-20) | 끄기 단계를 실제로 했는지 확인하지 않고 다음 단계로 넘김 | 같은 대화를 두 프로세스가 동시에 잡음 → 다른 계정 resume 이 `history-suppression` 을 기록 → 데스크톱 화면에서 답변 사라짐(파일 되돌림 + 원격 세션 재기동으로 복구) |

공통점: **처음 본 자료 하나로 결론**. 그래서 위 5번(부정 결과 재확인)이 특히 중요하다.

## 도구 함정 (부정 결과를 만드는 것들 — 실측)

- **zsh 수식자**: `"origin/$b:apps/..."` 에서 `$b:a` 가 경로 수식자로 해석돼 명령이 통째로 깨진다.
  → `"origin/${b}:apps/..."` 로 중괄호 필수
- **셸 grep(ugrep `-I`)**: NUL 한 바이트만 있어도 파일을 통째로 건너뛴다. `-a` 를 붙이거나 python 으로 재확인
- **LLM 1회 출력**: 원인 근거로 쓸 수 없다. **n≥3 + 대조군** 필수. 사소한 포맷·도메인 차이로 결과가 뒤집힌다

## 체크리스트 (말하기 전에)

- [ ] 이 문장의 근거가 코드·실측·문서 중 무엇인가. 대지 못하면 말하지 않는다
- [ ] 확인 범위를 문장에 붙였나
- [ ] 부정 결과라면 다른 방법으로 한 번 더 확인했나
- [ ] 반증 경로를 먼저 확인했나

> 프로젝트별 앵커는 각 repo `.claude/rules/` 에 둔다 (예: `00-assert-only-after-full-path.md`).

## ⛔ 단일 원인 단정 금지 — "설명이 되는 것"과 "원인인 것"은 다르다 (2026-09-04 추가)

사용자 지시: **"너는 전반적으로 너무 얕게 파악하고 바로 확답을 해버리는 아주 나쁜 습관이 있다.
거짓말이 아닌 듯 부정한 정보로 확신을 갖고 말하는 것 — 그게 최악이고 AI 로서 가장 안 좋은 체감 경험이다."**

### 무슨 일이 있었나 (2026-09-04)

"dev 배포가 3분 → 7~8분" 을 조사하며, git 로그에서 `verify_rollout`(롤아웃 대기) 도입 커밋을 찾고
**"원인은 이것"** 이라고 단정했다. 사용자가 젠킨스 Stage View 를 보여주자 실제 데이터는 정반대였다:

```
Checkout SCM        17s → 78s   (+61s)
Build               26s → 72s   (+46s)
Assemble            31s → 54s   (+23s)
Build Docker Image  48s → 113s  (+65s)
Verify Rollout      53s → 57s   (+4s)   ← 내가 "주범" 이라 한 것. 거의 유일하게 안 늘었다
```

`verify_rollout` 은 **증가 이전부터 이미 존재**했고(8/31 실측 46~56초) **증가하지도 않았다.**
나는 "이 변경이 시간을 더할 수 있다" 를 "이 변경이 늘어난 시간의 원인이다" 로 몰래 바꿔치기했다.

### 규칙

1. **"X 가 Y 를 설명할 수 있다" ≠ "X 가 Y 의 원인이다."**
   전자는 가설이고 후자는 결론이다. **증가분을 숫자로 배분하지 못하면 결론이 아니다.**
2. **총량 변화를 조사할 때는 반드시 구성요소별로 분해한다.** 단계·항목별 수치가 있는데 안 보고
   그럴듯한 하나를 집으면, 나머지 항목이 그 주장을 반증하고 있어도 못 본다.
3. **"주범·핵심 원인·때문이다" 를 쓰기 전에 자문한다** — *이 원인이 아니라면 무엇이 늘었어야 하나?
   그 값을 실제로 봤나?* 안 봤으면 **"후보"** 라고 쓴다.
4. **한 원인이 여러 항목의 동시 증가를 설명하는가?** 여러 항목이 같이 늘었으면 개별 코드 변경보다
   **공통 자원**(에이전트 CPU·디스크·캐시·네트워크)을 먼저 의심한다.
5. 사용자가 자료(스크린샷·로그·표)를 갖고 있을 가능성이 높은 주제면, **단정하기 전에 그 자료를 요청**한다.
   내 추론보다 그쪽이 싸고 정확하다.

> 체크: 결론 문장에서 "때문이다" 를 지우고 "후보다" 로 바꿔도 답변이 성립하나?
> 성립한다면 애초에 "때문이다" 라고 쓸 근거가 없었던 것이다.

### 내가 만든 것도 예외가 아니다 (2026-09-04 추가)

**시스템·봇·스크립트의 동작을 말하기 전에 그 코드를 먼저 읽는다.** 내가 만들었거나 방금 고친 것이라도 마찬가지다.

같은 날 두 번 밟았다.
1. 배포 지연 원인을 `verify_rollout` 하나로 단정 → 젠킨스 Stage View 가 반증 (그 단계만 안 늘었다)
2. 알림봇이 *"알림이 뜨면 자동으로 조사→티켓→PR 을 만든다"* 고 단정 → **중복제거·채널게이트·스레드무시가 이미 다 구현돼 있었다**
   (봇 코드의 중복 제거·건너뛰기 분기)

두 번 다 **"그럴듯한 동작 모델"을 코드 대신 사용했다.** 기억이나 설계 의도는 코드가 아니다.

**체크**: 시스템 동작을 서술하는 문장을 쓰기 전에 — *그 파일을 이 세션에서 열었나?* 안 열었으면 열고 나서 쓴다.
